# Architecture Decisions & Design Notes

This file contains important design decisions, future plans, tradeoffs, and discussions made during development.

It is intended to help future contributors (including future AI assistants) understand why certain choices were made.

---

# Authentication

## Decision

Use Google OAuth instead of traditional email/password authentication.

## Reasoning

Benefits:

* Faster onboarding
* No password storage
* No password reset workflow
* Simpler user experience

Current user roles:

```text
USER
ADMIN
```

---

# Rich Question Authoring

## Decision

Use Quill Editor for question creation/editing.

## Reasoning

Questions require:

* Bold text
* Italics
* Lists
* Code blocks
* Rich formatting

Quill generates HTML which is stored directly in MongoDB.

Example:

```html
<p>Given an integer array <strong>nums</strong>...</p>
```

During rendering Quill is NOT required.

The browser renders stored HTML directly.

# Code Editor

## Decision

Use Monaco Editor.

## Reasoning

Provides:

* VS Code-like experience
* Syntax highlighting
* Autocomplete
* Multi-language support in future

Used only for user code editing.

# Question Execution Model

Questions are designed in a LeetCode-style format.

Users implement:

```cpp

    ...

```

instead of writing a full program with main().

Every question stores:

## Starter Code

Displayed inside Monaco.

Example:

```cpp

    int twoSum(...) {

    }

```

---

## Execution Template

Stored separately.

Contains:

```cpp
LECO_USER_CODE
```

placeholder.

Example:

```cpp
#include <bits/stdc++.h>
using namespace std;

LECO_USER_CODE

int main() {
    ...
}
```

During execution:

```text
Execution Template
        +
User Code
        ↓
Final Source File
```

The placeholder:

```text
LECO_USER_CODE
```

is replaced by the user's submitted solution.

# Official Solution Storage

Implemented.

Each question stores:

```text
officialSolution  (String, admin-only)
```

in addition to starter code.

Stripped from all public API responses — only returned to ADMIN role.

Purpose:

* Generate expected outputs for testcases (via tcGenWorker)
* Validate custom testcases
* Future stress testing
* Future rejudging

---

# Test Cases

Implemented.

Separate collection.

```text
Question
    ↓
Many TestCases
```

Each testcase contains:

```text
input   (required)
output  (auto-generated by tcGenWorker using officialSolution)
```

Note: `isHidden` field removed — all testcases are hidden from users by design. There is no concept of public testcases in the DB; examples shown to users are stored directly on the Question document.

Output generation flow:

```text
Admin saves testcases
↓
tcGenQueue job enqueued
↓
tcGenWorker runs officialSolution through Docker
↓
Saves output to each TestCase document
```

# Run vs Submit

These are intentionally different actions.

---

## Run

Purpose:

Quick feedback.

Characteristics:

* Uses example testcases or custom input
* No database submission record
* No history saved
* User expects very low latency

Output:

```text
stdout
stderr
```

Future:

Expected output may be generated using the official solution.

---

## Submit

Purpose:

Official judging.

Characteristics:

* Creates Submission record
* Runs hidden testcases
* Generates official verdict
* Appears in submission history

Verdicts:

```text
AC
WA
CE
RE
TLE
MLE
SYSTEM_ERROR
```

API returns full result synchronously — frontend waits on the single HTTP response, no polling required.

# Queue Architecture

Implemented.

Three separate queues:

```text
runQueue      — run jobs (no retry, concurrency 1)
submitQueue   — submit jobs (retry 3x exponential, concurrency 1)
tcGenQueue    — testcase output generation (retry 2x, concurrency 1)
```

Reasoning:

User behavior heavily favors Run.

Typical workflow:

```text
Run
Run
Run
Run
Submit
```

Users expect Run to feel nearly instant.

Submit can tolerate longer latency.

Therefore latency is prioritized over maximum worker utilization.

All workers run in-process alongside the Express API server.

Concurrency is 1 for all queues currently — to be scaled later.

`QueueEvents` instances are module-level singletons (one per queue). This avoids the race condition where a per-request listener misses the `completed` event if the worker finishes before the listener attaches. `job.waitUntilFinished(queueEvents)` is used for synchronous result waiting.

Reason:

Potentially large latency improvement.

# BullMQ

Implemented.

Architecture:

```text
Frontend
    ↓
API
    ↓
BullMQ
    ↓
Redis
    ↓
Worker
```

Jobs contain minimal payloads:

```text
submitQueue  →  { submissionId }
runQueue     →  { questionId, language, code }
tcGenQueue   →  { questionId }
```

Workers load full data from MongoDB. This keeps job payloads small and avoids stale data in the queue.

---

# Docker

Implemented.

Execution architecture:

```text
Worker
    ↓
Write source to host temp dir
    ↓
Mount temp dir into Docker Container (gcc:13)
    ↓
Compile (g++ -O2)
    ↓
Execute (one process per testcase, stdin from input file)
    ↓
Collect stdout / detect TLE / MLE / RE
    ↓
Clean up temp dir
```

Purpose:

* Isolation
* Security
* Resource limits

Resource limits enforced per container:

```text
--memory=<memoryLimit>m
--memory-swap=<memoryLimit>m   (swap disabled — OOM kill fires cleanly)
--cpus=1
--network=none
```

MLE detected via exit code 137 (Docker OOM SIGKILL).
TLE detected via process timeout.
RE detected via non-zero exit code (other than 137).

# Output Comparison

Each question stores a `comparatorType` field used by all workers when comparing actual vs expected output.

Current options:

```text
EXACT_MATCH       — trims whitespace, normalises line endings, compares strings
FLOAT_EPSILON     — parses both as float, accepts if |actual - expected| ≤ 1e-6
UNORDERED_VECTOR  — splits into tokens, sorts both, compares
CUSTOM            — not yet implemented, falls back to EXACT_MATCH
```

Default: `EXACT_MATCH`

## Proposed Direction

Questions will eventually have:

```text
version
```

Submissions will store:

```text
judgedAgainstVersion
```

Example:

```text
Question Version 7

Submission judged on Version 5
```

allowing stale submissions to be identified.

Possible strategies:

```text
ALL

AC_ONLY

LATEST_PER_USER

LATEST_AC_AND_REJECTED_PER_USER
```

No final decision yet.

## Queue Priority

Future direction:

```text
Run Jobs
    Highest Priority

Submit Jobs
    Medium Priority

Rejudge Jobs
    Lowest Priority
```

Reason:

Active users should never wait behind maintenance operations.

# Development Philosophy

Use AI aggressively for:

* Boilerplate
* CRUD
* Forms
* Repetitive code

Developer remains responsible for:

* Architecture
* Data flow
* Queue design
* Security
* Worker lifecycle
* Infrastructure decisions

Goal is not merely to build the project.

Goal is to understand how real online judges work internally.
